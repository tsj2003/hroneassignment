# REVIEW.md

The starter runs the happy path. The defects below are in the original `app/main.py` (line numbers refer to that file). Each one fails a specific input, a race, or the 100k-record plan.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health`, lines 72–74 | Always returns 200. It never pings MongoDB, so a dead database still looks ready. | Stop MongoDB and `GET /health`. The starter returns 200; the runner then sends the suite at a database that is down. | Ping with `admin.command("ping")`. Return 200 `{"status":"ok"}` only when that succeeds, otherwise 503. |
| 2 | Client setup, lines 20–23 | `mongodb://localhost:27017` and `attendance_db` are hard-coded fallbacks, and the client is not timezone-aware. PyMongo therefore hands back naive datetimes. | Unset `MONGO_URI` and the process still dials localhost. A UTC grader and an IST laptop turn the same punch into different calendar dates. | Read `MONGO_URI` and `MONGO_DB` from the environment. `load_dotenv()` does not override them. Connect with `tz_aware=True` and UTC. |
| 3 | Startup, whole file | No indexes are created. Uniqueness of `emp_code` and of (`emp_code`, `date`) is not enforced, and every list or analytics query collection-scans. | Two parallel `POST /employees` with the same code can both return 201. `explain` on `/attendance` shows `COLLSCAN` once the collection is large. | Create indexes idempotently at startup, including the two unique indexes, and hint the list/analytics plans so they stay `IXSCAN`. |
| 4 | `compute_late_minutes`, lines 33–37 | Grace is applied to already-floored minutes (`minutes > 10`). A punch 10 minutes and 1 second after shift start floors to 10 and is treated as on time. Late minutes are also measured from the wrong instant: `replace(hour, minute)` keeps the punch's timezone instead of building shift start in IST, and an overnight punch before `shift_end` is compared with shift start on the punch's own calendar day. | Shift `09:30`, punch `09:40:00` → 0 (correct) but `09:40:01` → 0 (must be 10) and `10:15:59` is only right by accident. Overnight shift `22:00–06:00`, punch `05:29` IST the next morning returns 0 instead of 449. | Truncate to seconds, anchor shift start on the attendance date in IST, and return 0 unless the punch is strictly after 10:00. When it is late, floor the minutes since shift start. |
| 5 | `compute_work_hours`, lines 40–41 | `round(..., 2)` is banker's rounding, and the inputs are not truncated to seconds first. R4 requires half-up. | 3618 seconds is exactly 1.005 hours. The starter returns `1.0`. Half-up is `1.01`. `round(2.675, 2)` is the same bug (`2.67` instead of `2.68`). | Divide whole seconds by 3600 with `Decimal` and `ROUND_HALF_UP`. |
| 6 | `compute_overtime`, lines 44–47 | There is no 30-minute minimum, and `shift_end` is placed on the attendance date. For an overnight shift that end is about 24 hours too early. A naive punch compared with an aware end also raises `TypeError` (500). | Sample day 1 is out at 18:35 against an 18:30 end: the starter returns 5, the stored value is 0. EMP0005 (22:00–06:00, out 06:40) returns a few hundred minutes instead of 40. | Put an overnight end on the next calendar day. Floor the minutes, and return 0 when that is under 30. |
| 7 | `create_employee`, lines 77–85 | Check-then-insert loses the race. `created_at = datetime.now()` is a naive local datetime and is returned as an ISO string, not epoch milliseconds. `emp_code`, email, shift pattern, a real `joined_on`, and `shift_start != shift_end` are not validated. | Two parallel creates of `EMP0099` can both return 201. `{"emp_code":"nope","email":"bad",...}` returns 201. `created_at` in the body is a string. `shift_start == shift_end` is stored. | Validate with the contract patterns. Insert directly and map `DuplicateKeyError` to 409. Store a UTC instant truncated to seconds and return it as epoch milliseconds. |
| 8 | `list_employees`, lines 88–96 | `skip = page * page_size` skips the first page. `total` ignores the department filter. Results are not sorted by `emp_code`. `page_size` is not capped at 100. `created_at` is still a datetime. | With six employees, `page=1&page_size=1` returns `EMP0002` (or whoever is second) and omits `EMP0001`. `department=Engineering` still reports `total` equal to the whole collection. | Skip `(page - 1) * page_size`, count the filtered query, sort and hint `emp_code`, cap `page_size` at 100, and serialize `created_at`. |
| 9 | `punch_in`, lines 99–121 | An unknown employee raises `KeyError` (500). `fromtimestamp` without a timezone uses the server's local zone, so the attendance date is not the IST date and overnight shifts are ignored. Sub-second instants are not truncated. `status` accepts `ABSENT` and `LEAVE`. A seconds-scale `punched_at` is accepted. The handler checks then inserts, and the response includes `id` plus raw datetimes. | `emp_code` that does not exist → 500. Punch `05:29` IST on an overnight shift is stored on the wrong date. `punched_at: 1700000000` → 201. Two parallel punch-ins for the same shift can both return 201. The body contains `id`. | 404 when the employee is missing. Truncate to seconds, compute the date with R1, restrict status to `PRESENT`/`WFH`/`ON_DUTY`, reject instants below `1e11`. Insert against the unique `(emp_code, date)` index and return 409 on a duplicate. Response has no `id`; instants are epoch milliseconds. |
| 10 | `list_attendance`, lines 123–150 | The handler loads every matching document, sorts in Python by `date` only, and paginates the list in memory. `total` is that list's length, so a 100k collection is read on every page. Same-day rows are not ordered by `emp_code`. Each item gains an `id` and keeps BSON datetimes. A legacy document with no `history` or `half_day` is returned missing those fields. `date_from > date_to` is not 422, and `page_size` is unbounded. | `date_from=2026-07-06&date_to=2026-07-06` does not stably put `EMP0001` before `EMP0003`. `GET` of EMP0002's 2026-07-14 record has no `history` and no `half_day`. `date_from=2026-07-10&date_to=2026-07-01` returns 200. On 100k rows the request gets slow and `explain` is a collection scan. | Filter, sort (`date` desc, `emp_code` asc), skip and limit in MongoDB on a matching index. Count with the same filter. Serialize instants, default a missing history to `[]` and a missing `half_day` to false, reject an inverted range with 422, and cap `page_size`. |

Looked at, and not a defect:

- `load_dotenv()` is called without `override=True`, so a real environment variable already beats `.env`. That matches the contract.
- `list_attendance` uses `(page - 1) * page_size`. The off-by-one is only in `list_employees`.
- Punch-in does initialise `work_hours`, `overtime_minutes`, `half_day` and `history` to the right empty values. The date, the race, and the response shape around them were the defects.
- `list_employees` projects `_id` away. The problem was the page math, the count, the sort, and `created_at`, not the identifier leaking.
